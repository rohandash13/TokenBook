# M4 design notes (controller-authored; binding)

Milestone 4 = reservations + receipts + delivery check + idempotency + duplicate catch. Spec §8, §13:
"Parallel sub-agents cannot exceed budget; timeout does not double-pay; duplicate purchase reused ('saved $5')."
Builds on M1–M3 (read the actual repo; M3 is being implemented from docs/superpowers/plans/2026-10-24-countersign-m3.md right now — treat its types/functions (Hold, holds in pay_and_fetch, human_approval decisions, approve endpoint paying a held request, get_hold) as current. Read DECISIONS and the M2/M3 plan headers for D1–D34.)

## 1. Atomic budget reservations (INV: parallel sub-agents cannot overspend a task budget)
Reservation { reservationId, taskId, paymentRequestId, amountUsd, state: "reserved"|"committed"|"released", createdAt, updatedAt }.
Store gains atomic `reserve(taskId, paymentRequestId, amountUsd, budgetUsd): Promise<{ ok: true, reservation } | { ok: false, remainingUsd }>` — a single synchronous critical section in MemoryStore (no await between reading outstanding total and inserting) so concurrent calls via Promise.all cannot both succeed when only one fits. Outstanding = sum of reservations in reserved or committed state for the task (use atomic integer math like floors.ts toAtomic). `commit(reservationId)`, `release(reservationId)`, `listReservations(taskId)`. Idempotent state transitions (commit twice = no-op; release after commit = refused/no-op).
Flow in pay_and_fetch: after tracing/floors compute the quote-charged amount; reserve BEFORE deciding (spec: "reserve before the decision"). If reserve fails → block (reason "budget exhausted"), decision logged, nothing paid. If final verdict is hold/block → release. If approve and pay settles → commit. If pay definitively fails → release. If pay outcome is AMBIGUOUS (throw/timeout) → keep reserved (NOT released), mark pending (see §3). Holds: a held payment keeps NO reservation while waiting (so a long hold does not starve the budget); on human approval re-reserve atomically (approve fails 409 if budget no longer fits), then pay. The existing floors budget check (budgetRemainingUsd from decisions) is replaced by reservations as the source of truth; keep the floor function but feed it reservation-based remaining, and keep its tests green.

## 2. Idempotency key + duplicate catch
idempotencyKey = sha256(taskId + "|" + canonical({ url, payeeDomain: quote payee, amountAtomic, tier: quote tier, quantity })) — only payment-relevant, quote-charged fields. NOT the agent's purpose text or other free text. (M2 review found purpose-sensitive keys defeat retry dedupe.)
New Store collection `payments` keyed by idempotencyKey: { idempotencyKey, taskId, state: "pending"|"settled"|"failed"|"unknown", receiptId?, firstDecisionId, result?, createdAt, updatedAt } with atomic `claimPayment(key, ...)` → { claimed: true } | { claimed: false, existing }.
Duplicate rule (spec §7): same task + same idempotency key within the window (config DUPLICATE_WINDOW_MS, default 10 min): if existing.state === "settled" → REUSE the cached result: respond status "approved" (or the original status), with data from the first fetch, field `reused: true`, `savedUsd = amount`, append a decision kind "duplicate_reused" with costUsd 0, verdict approve, reasons ["duplicate of decision X; payment skipped; saved $N"]. Do NOT pay again, do NOT reserve again. If existing.state is "pending"/"unknown" → return held-like status "pending" (reason "payment outcome not yet confirmed; will not pay twice") and do not pay. If existing failed definitively → allow a fresh attempt (new claim).
"Saved $5" demo: arena gets a priced "report" endpoint (e.g. /api/report, category research, $5.00 per call, unit "call") so the duplicate saving shows as $5. Add to arena + catalog.json.

## 3. Timeout / ambiguous outcome (INV5: timeouts never trigger a second payment)
SimulatedExecutor gains injectable failure modes (config only used by tests/arena failure scenarios): "timeout_then_success": the first pay() for a key rejects with an ExecutorTimeoutError AFTER the arena has already recorded/settled the payment (simulating the response being lost); a later status check shows settled. Add to the Executor interface `confirm(idempotencyKey, quote): Promise<PayOutcome | { status: "unknown" }>`: asks the arena/facilitator whether a payment with this key settled. The arena records settled payments by idempotency key (header x-sim-payment carries the key already) and exposes GET /payments/:key → { settled: boolean, data? } (simulated; label it). Executor.pay never retries internally.
pay_and_fetch on pay() throwing/timeout: mark payment state "unknown", keep reservation reserved, append executor_failure/ambiguous decision (kind "payment_unconfirmed") WITH the error cause in reasons, then call executor.confirm(key) (bounded retries, e.g. 3, small backoff configurable, default 0ms in tests): if confirmed settled → commit reservation, record receipt, state settled, return data (status approved, reason "recovered after timeout; confirmed settled; paid once"). If confirmed NOT settled → ONLY THEN may a single retry pay() occur (same key; arena rejects a replay of a settled key, i.e. arena treats same key twice as idempotent: second pay with an already-settled key returns the original data without charging again — implement this arena-side so even a buggy retry cannot double-charge, and assert chargeCount in tests). If still unknown after confirm retries → state stays "unknown", reservation stays reserved, return status "held" with reason "payment outcome unknown; manual reconciliation" (never a second payment).
Arena records chargeCount per key (test hook GET /_debug/charges/:key or injected counter) so tests can assert exactly-once charging, including "double charge" failure mode: arena mode `double_charge` where the vendor's endpoint charges twice if called twice with different keys is NOT our concern; but the arena mode "charge_twice_on_retry" (ignores idempotency) lets the delivery/receipt check catch paid != quoted? No — keep scope: only timeout_then_success, empty_response, bad_schema, plus the idempotent-replay behaviour above.

## 4. Receipts + delivery check (spec §8)
Receipt { receiptId, decisionId, taskId, quotedUsd, paidUsd, deliveryStatus: "ok"|"empty"|"bad_format"|"unknown", txRef, createdAt }.
Delivery check (rule-based, packages/gateway/src/delivery.ts): `checkDelivery({ data, expectedSchema, quotedAtomic, paidAtomic })` → { status, reasons }: "empty" if data null/undefined/{}/[]/""; "bad_format" if it doesn't satisfy the endpoint's expected zod schema (config per catalog entry: weather → {city, tier, tempC, conditions}; forecast → ...; crypto → ...; report → ...), "ok" otherwise; additionally paid != quoted → reasons + deliveryStatus "bad_format"? No: add a separate flag `amountMismatch: true` on the receipt and force deliveryStatus != "ok". Payee record: `payees { payeeId, domain, crsStatus, liens, ofacHit, firstSeenAt, deliveryFailures }` (M5 fills CRS; M4 owns deliveryFailures): on non-ok delivery increment payees.deliveryFailures for the quote payee (create record on first sight with defaults). The judge input's payeeRecord.deliveryFailures now comes from the store (it was constant 0). Floors: deliveryFailures >= 2 (config DELIVERY_FAILURE_HOLD_AT, default 2) → floor HOLD "vendor failed delivery N times" — a failed delivery visibly lowers a vendor's standing (spec demo requirement). Arena failure modes: `?mode=empty` and `?mode=bad_schema` query params on a vendor endpoint (arena-only, never part of the signed resource semantic problem: the mode is part of the resource URL so it is bound by the payment signature) returning 200 with empty/malformed body after payment.
Tier 1 and receipts: a Tier 1 auto-approval still produces a receipt and delivery check.

## 5. Dashboard-facing read APIs (for M7; build now, small)
GET /admin/decisions?taskId= (list, newest first), GET /admin/decisions/:id (with evidence), GET /admin/receipts?taskId=, GET /admin/budget/:taskId → { budgetUsd, reservedUsd, committedUsd, remainingUsd }, GET /admin/chain/verify → { ok, brokenAt? , length, headHash }, GET /admin/payees. All unauthenticated like /admin/tasks (D13). Metrics helper `computeMetrics(store)`: autonomyRate = decisions approved at tier 1 or tier 2 without human / all payment decisions (excluding duplicate_reused and human kinds in the denominator rules documented); tier1Count, tier2Count, holds, blocks, avgTier1LatencyMs, totalCostUsd (sum of non-null costUsd), moneySavedUsd (sum of savedUsd of duplicate_reused). Real numbers only, computed from the store; no placeholders.

## Acceptance (tests/m4-acceptance.test.ts over the HTTP stack, fake judge)
1. Parallel: task budget $0.30, 5 concurrent identical-in-policy $0.10 purchases with distinct requests (different cities) via Promise.all → at most 3 approved, the rest blocked "budget exhausted"; reservations sum <= budget; executor.pay called exactly (approved count) times.
2. Timeout: executor mode timeout_then_success → pay_and_fetch returns approved after confirm, arena chargeCount for the key === 1, executor.pay call count === 1 (no retry because confirm shows settled); a second variant where confirm says not-settled → exactly one retry, chargeCount === 1.
3. Unknown outcome: confirm keeps returning unknown → status held "outcome unknown", reservation still reserved, no second pay.
4. Duplicate: same purchase twice → second returns reused:true, savedUsd 5, pay called once, a duplicate_reused decision logged; with a different city/params it is NOT a duplicate.
5. Delivery: vendor returns empty → receipt deliveryStatus "empty", payees.deliveryFailures === 1; after the second empty delivery the next purchase from that vendor is floored to HOLD with reason about failed deliveries.
6. Idempotency key ignores purpose: two requests differing only in purpose text produce the same key; retry with reworded purpose after a timeout does not double-charge.
7. INV5 todo test becomes real (replace the it.todo in tests/invariants).
8. Reservation state machine unit tests, atomic reserve concurrency unit test (Promise.all on the store), delivery checker unit tests, metrics unit tests, hash chain still verifies after all new decision kinds.
